# DEC-012 · Placar em Sorted Set com Write-Through, ao lado do Cache-Aside do top 100

- **Contexto:** a especificação de BD2 sugere, para "Plataforma de Ensino EAD / Gamificação", "Redis (Sorted Sets): placar de líderes em tempo real", e pede a demonstração de padrões de sincronização entre SQL e NoSQL (Write-Through, Cache-Aside, Event-Driven). A DEC-005 tinha escolhido string JSON para o top 100, com o Sorted Set como evolução. Faltava a posição de um usuário qualquer: no SQL, ela exige numerar o ranking inteiro (`row_number()`) a cada consulta.
- **Decisão:** manter a DEC-005 para o top 100 (Cache-Aside, `ranking:geral:v1`, TTL 60 s) e acrescentar o placar `ranking:placar:v1` (Sorted Set com todos os participantes). Membro = id do usuário; score = `total_pontos × 10^10 + (10^10 − segundos da última concessão)`, que codifica a RN12 num número só. Sincronização por **Write-Through**: depois do COMMIT de uma aprovação nova, a API lê o total do membro no PostgreSQL e faz `ZADD`, num script Lua que só grava se o placar existir. O placar é reconstruído do PostgreSQL quando não existe (Redis reiniciado sem disco ou TTL de 10 min vencido). Rota nova: `GET /ranking/eu`.
- **Alternativas:** trocar o top 100 também para o Sorted Set (descartada: precisaria de mais uma estrutura para os nomes, e o Cache-Aside já é um padrão a demonstrar); calcular a posição sempre no SQL (descartada: medido, 148 req/s contra 1.304 req/s com o Redis).
- **Limites declarados:** empate de pontos no mesmo segundo cai na ordem do membro no Redis, e não do id; conferido em 12/11/2026 que não ocorre na carga (`scripts/conferir-placar.sh`: 0 diferenças em 5.876). Score exato até cerca de 900.000 pontos. Uma corrida rara entre a reconstrução e uma aprovação pode deixar o placar defasado por até 10 min (TTL).
- **Evidência:** `docs/resultados/testes-api.txt` (Redis x SQL em 5 usuários, Write-Through, Redis fora e Redis de volta vazio) e `docs/resultados/cache.txt` (vazão).
